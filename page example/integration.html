Case study

One integration, every customer

How facility, field-service and CMMS platforms use Makini to turn each new client into a connection — not an engineering project.
The Facilities Group
Integrated Facility Management
Problem

TFG runs preventive maintenance at 30,000+ buildings across North America. Every facility owner they serve runs a different FSM — Corrigo, Fexa, ServiceChannel — so every new account historically meant another integration.

Before

TFG engineers rebuilt the same work-order, status, notes and attachment sync from scratch for every new FSM. The cost of saying “yes” to a new client kept rising with every win.

After

TFG’s JAN-IT platform speaks one Makini object model. Each new client tenant is a connection, not an engineering project — eight bidirectional workflows cover PM and non-PM work orders, status, check-in/check-out, notes and attachments across every supported FSM.

MCIMby Fulcrum Collaborations
Mission-Critical Facility Management
Problem

MCIM is the EAM/CMMS/APM platform for mission-critical data centers. Subscribers like NTT also run ERP, ITSM and DCIM tools where the same asset and work-order data has to live — but data was locked inside each system.

Before

Every subscriber expected MCIM to deliver integrations into their stack, but building them one-by-one meant slow onboarding and a growing backlog of one-off connectors. New subscribers waited months for basic data flow.

After

MCIM uses Makini’s Universal API to deliver hundreds of pre-built ERP, MES and WMS integrations to subscribers like NTT through one common connector layer. New subscriber onboarding is a connection, not a custom build.

ServiceTitan
Field Service Management
Problem

Commercial contractors on ServiceTitan get work assignments from the CMMS platforms their facility-owner clients run — Corrigo, Corrigo Pro, ServiceChannel, Fexa, Verisae, Maximo, FM:Systems. Each platform is a different integration with a different data shape.

Before

Contractors manually retyped work orders from each CMMS into ServiceTitan as Bookings and logged into multiple systems to push status updates — Dispatched, Arrived, Working, Completed.

After

Work orders flow from any supported CMMS into ServiceTitan as Bookings automatically. Accept/Decline responses and technician check-in/check-out events sync back to the CMMS as activity-log entries — one Makini connection per contractor’s CMMS account.

Brightly SoftwareAsset Essentials
CMMS / EAM
Problem

Brightly’s customers like Licking County Utilities were running legacy on-premises CMMSes (MP2 on Antero, Tier II) and needed to move to Asset Essentials — but migration meant pulling sites, assets, work orders and history out of an aging system before any of it could be useful in the new one.

Before

Each subscriber migration was a custom extraction project — sites, hierarchies, assets and work-order history had to be pulled, mapped and loaded by hand, slowing every onboarding.

After

Brightly uses Makini to extract data directly from the legacy CMMS and migrate it into Asset Essentials inside a 30-day project window — sites, assets and work-order history flow into AE through one repeatable connector pattern instead of a one-off ETL each time.

Frequently Asked Questions

Have any questions? We’re here to help You

How long does it take to integrate with Makini?

Integration timelines vary by complexity. For standard implementations with no customizations, connections can be live within 1-2 weeks. This includes authentication setup and basic workflow configuration. For implementations requiring custom workflows or specific business logic, timelines typically range from 2-6 weeks depending on the scope. Complex enterprise deployments with multiple systems and custom requirements may take 6-10 weeks. These timelines are significantly shorter than traditional integration projects, which often take 2-24 months.

What fields are supported for purchase orders?

Makini's purchase order data model includes comprehensive field coverage across all major ERP systems. Standard fields include order number, line items, vendor information, quantities, unit prices, dates (order date, required date, delivery date), status, currency, ship-to and bill-to addresses, payment terms, and custom fields. Each line item includes product/material codes, descriptions, quantities, unit of measure, pricing, and delivery information. The specific fields available depend on the source system's capabilities. You can view the complete field mapping for any connected system in the Makini dashboard, and custom fields can be added as needed for your specific requirements.

How do I check sync status?

Makini provides a /sync-status API endpoint that returns the current synchronization state for a connection. The response includes the last successful sync timestamp, sync status (in progress, completed, failed), any error messages, and the next scheduled sync time. You can query this endpoint to monitor sync health and detect issues. For workflow-based syncs using Makini Flows, each workflow execution is logged with detailed status information including start time, completion time, success/failure status, and any errors encountered. The Makini dashboard also provides visual sync status monitoring across all connections.

Does Makini support multi-region deployments?

Yes, Makini supports multi-region deployments for customers requiring data residency in specific regions or needing high availability across geographies. Each region runs an independent instance of Makini with its own infrastructure, ensuring data remains within the specified region. Multi-region deployments are most common for self-hosted installations where customers want instances in multiple AWS regions or data centers. For cloud deployments, we can discuss region-specific hosting based on your requirements. Multi-region support ensures compliance with data localization regulations and provides geographic redundancy for mission-critical integrations.
